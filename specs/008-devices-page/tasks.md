- [x] T031 **`POST /devices/pairings` could never pair inside the DSH Host** — found on the live product path, fixed, reviewer-passed, verified. Symptom: the session reached `failed` with `code:"unreachable"` ("could not connect to the remote gateway") while `/mgw/pending` stayed empty, yet calling the same `claimWithOtp` from plain Node against the same URL and OTP paired fine. Root cause (a): `openPinnedSocket` passed the pinned leaf as `ca` and compared the pin inside `checkServerIdentity`, so **chain building** decided trust; the gateway leaf is self-signed with `basicConstraints CA:FALSE` (`plugins/mobile-gateway/lib/tls.mjs:87`), which OpenSSL accepts as its own anchor but the Host runtime (Electron 44.7.0 / node 24.21.0, BoringSSL, `process.versions.openssl` = 0.0.0) rejects with `UNABLE_TO_VERIFY_LEAF_SIGNATURE`; Node then skips `checkServerIdentity` entirely, so the pin was never compared and `ws` failed before any `pairing-proof` frame. Fix: `openPinnedTlsSocket()` performs one `tls.connect({rejectUnauthorized:false})`, hashes `getPeerCertificate(true).raw`, refuses a mismatch **before** the socket is handed to `ws` via `createConnection`, and refuses a zero-length buffer outright — so no credential byte precedes the check and one handshake replaces probe+connect (no swap window). Proof: `test/pairing-trust.test.mjs` seeds a leaf issued by a CA the client never receives (no runtime can chain it), asserts the control failure, then drives `POST /devices/pairings` → pending → approve → `approved` → `online`; the control connection is bounded at 8000 ms and a stall fails instead of hanging; reverting the fix makes the route test fail.

- [x] T038 **The TLS listener survives a busy port.** `openLanListener()` keeps one `https.Server` and, on an `error` with `code === 'EADDRINUSE'` (non-zero configured port, still the current listener, not yet listening, not disposed, under 10 attempts), logs `TLS listener port <p> is busy; trying <p+1>` and re-`listen()`s the same server on the next port. - [x] T039 **The Devices page warns when the listen port is a bad choice.** Measured fact that drove it: the dynamic/ephemeral TCP range is `49152-65535` by default on Windows but is frequently retuned, and the machine this was built on runs `1024-15000` — which is why the old default `3081` could collide with an outbound connection's source port. The card flags `port < 15000` or `port >= 49152`, names `20000-39999` as the safe band and says the gateway now moves to the next free port by itself; it stays completely silent for a safe port (including the new default `30081`). When the listener is down with `EADDRINUSE`, the raw error is still shown verbatim and a separate note explains a busy port without repeating the token.
